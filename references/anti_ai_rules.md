Этот файл содержит полный свод правил для генерации текста, который проходит детекторы Антиплагиат.ВУЗ, GPTZero, ZeroGPT, GigaCheck.

**Читай этот файл ПЕРЕД генерацией каждого раздела.**

## 1. КАК РАБОТАЮТ ДЕТЕКТОРЫ

### Три главные метрики

**Perplexity (предсказуемость):** ИИ — низкая (слова предсказуемы), человек — высокая (неожиданные обороты). Твоя задача: неожиданные синонимы, профессиональный жаргон, нестандартный порядок слов.

**Burstiness (вариативность):** ИИ — равномерный ритм, человек — вспышками (то длинно, то коротко). Твоя задача: после длинного предложения (25+ слов) — короткое (5-8 слов).

**Zipf-отклонение:** ИИ перепроизводит высокочастотные союзы, недопроизводит среднечастотные слова. Твоя задача: разнообразная лексика, не перегружай союзами.

### Что дополнительно ловит Антиплагиат.ВУЗ

- Паттерн «обобщение → двоеточие → список → вывод» (при регулярном повторении)
- Цепочки отглагольных существительных
- Тавтологические повторы (один смысл разными словами подряд)
- Регулярные повторы одних и тех же связок
- Пробелы перед знаками препинания
- Аномалии пунктуации

## 2. ЧЁРНЫЙ СПИСОК СЛОВ И ФРАЗ

### КАТЕГОРИЯ А: АБСОЛЮТНЫЙ ЗАПРЕТ (0 вхождений)

Коэффициент ИИ-детекции 8×-35×. Ни одного вхождения на весь текст.

**Фразы-маркеры «отметить»:**
- «Важно отметить, что» (9×) → убрать полностью
- «Стоит отметить, что» (9×) → убрать полностью
- «Следует отметить, что» (3.4×) → убрать полностью
- «Необходимо отметить» (10×) → убрать полностью
- «Можно отметить, что» (8×) → убрать полностью
- «Можно заметить, что» (14×) → убрать полностью
- «Необходимо подчеркнуть» (10×) → убрать полностью
- «Нельзя не упомянуть» / «Нельзя не отметить» → убрать полностью

**Шаблонные зачины:**
- «В современном мире» → убрать, начать с конкретики
- «В современном быстро меняющемся мире» → убрать полностью
- «В настоящее время» → Сейчас / К 2025 году
- «На сегодняшний день» → К моменту разработки

**Фразы «роль»:**
- «Играет важную роль» → конкретный глагол действия
- «Играет ключевую роль» → влияет на / определяет
- «Играет значительную роль» → существенно влияет на

**Signposting (навигационные фразы):**
- «Рассмотрим подробнее» → убрать, сразу рассматривать
- «В данном подразделе рассматривается» → убрать, сразу к сути
- «Перейдём к анализу» → убрать
- «Давайте разберём» → убрать
- «Далее будет рассмотрено» → убрать

**Маркеры выводов:**
- «В заключение стоит сказать» → убрать
- «Подводя итог» → убрать
- «Таким образом, можно сделать вывод» → конкретный вывод без вводной

**Authority tropes:**
- «В сущности» → убрать
- «Реальный вопрос заключается в» → убрать
- «Фундаментально важно понимать» → убрать
- «Суть проблемы в том» → Проблема в том

**Promotional (рекламные):**
- «Неизгладимый след» / «Поворотный момент» / «Погружаться в»
- «Бесшовный» / «Синергетический» / «Революционный подход» / «Прорывной»
- «Инновационный» (без конкретики) → конкретное описание

**Прочие:**
- «Это не просто X, а Y» → переформулировать без шаблона
- «Вышеупомянутый» → этот / указанный
- «Нижеследующий» → убрать

### КАТЕГОРИЯ Б: СТРОГОЕ ОГРАНИЧЕНИЕ (1-2 раза на весь текст)

| Слово/фраза | Максимум | Замены |
|---|---|---|
| является | 2-3 раза | тире; представляет собой |
| данный (= этот) | 2 раза | этот; указанный; рассматриваемый |
| таким образом | 2 раза (3.2×) | итог:; поэтому; следовательно |
| в рамках | 2 раза | при; во время; в ходе |
| обеспечивает | 2 раза | ускоряет; упрощает; конкретный глагол |
| позволяет | 3 раза | с его помощью можно; благодаря X |
| не только..., но и | 1 раз | переформулировать |
| в связи с этим | 2 раза | поэтому; из-за этого |
| демонстрирует | 2 раза | показывает; видно что |
| во-первых/во-вторых/в-третьих | 1 серия (15×/35×) | разбить на абзацы |
| с одной/другой стороны | 1 раз (4.3×/6×) | противопоставление |
| следует учитывать, что | 1 раз (7×) | убрать |
| служит / выступает в роли | 2 раза | тире; прямой глагол |

### КАТЕГОРИЯ В: НЕЖЕЛАТЕЛЬНО (1-2 раза, не в соседних абзацах)

- осуществлять → выполнять; проводить; делать
- реализовать → создать; написать; разработать; собрать
- функционал → возможности; набор функций
- оптимальный (без уточнения) → подходящий; удобный; быстрый
- эффективный (без метрики) → быстрый; экономичный; (указать метрику!)
- релевантный → подходящий; соответствующий; нужный
- имплементация → реализация; создание; внедрение
- в условиях → при; когда; если
- как правило → обычно; в большинстве случаев

## 3. СТРУКТУРНЫЕ ПРАВИЛА

### Правило 1: РИТМ ПРЕДЛОЖЕНИЙ

Каждый абзац — предложения РАЗНОЙ длины. Формула: короткое → длинное → короткое.

ПЛОХО (все ~15 слов, монотонный ритм):
> Для разработки клиентской части было решено использовать язык JavaScript. Язык JavaScript позволяет создавать интерактивные элементы на веб-страницах. Выбор этого языка обусловлен широкой поддержкой браузерами.

ХОРОШО (ритм 5 / 22 / 7 / 19 слов):
> Клиентская часть написана на JavaScript. Выбор пал на этот язык из-за универсальности: он работает во всех современных браузерах без дополнительных плагинов и транспиляции. Альтернативой был TypeScript. Однако для проекта такого масштаба строгая типизация создала бы избыточную сложность без ощутимых преимуществ.

Инструкция: после каждого длинного предложения (20+ слов) вставляй короткое (5-8 слов).

### Правило 2: НАЧАЛА АБЗАЦЕВ

Никогда не начинай два соседних абзаца одинаково. Чередуй:

- С конкретного факта: «Файл config.js занимает 12 КБ...»
- С обстоятельства: «На этапе проектирования было решено...»
- С результата: «Итоговая структура включает 14 модулей...»
- С причины: «Поскольку система работает с несколькими API...»
- С деепричастного оборота: «Проанализировав существующие решения...»
- С противопоставления: «В отличие от монолитных приложений...»
- С числительного: «Три основных модуля отвечают за...»
- С цитаты/ссылки: «Согласно документации MDN [3]...»
- С отсылки к предыдущему: «Описанный выше подход к маршрутизации...»

Проверка: первые 2-3 слова каждого абзаца. Если два соседних одинаковы — переписать.

### Правило 3: АНТИПАТТЕРН «СПИСОК»

Антиплагиат.ВУЗ ловит паттерн: «обобщение → двоеточие → список → вывод».

Если больше 2 таких конструкций подряд в разделе — детектор флагует.

Как нарушить:
- Иногда начни с деталей, обобщи в конце
- Иногда встрой перечисление в предложение БЕЗ двоеточия
- Иногда используй таблицу вместо списка
- Иногда распиши каждый пункт отдельным абзацем

### Правило 4: ИНФОРМАЦИОННАЯ ПЛОТНОСТЬ

Каждая страница должна содержать минимум:
- 2-3 конкретных технических термина (не общих слов)
- 1-2 названия файлов, функций, переменных, библиотек из проекта
- 1 числовой факт (версия, размер, количество, процент)

ПЛОХО:
> Серверная часть приложения обеспечивает обработку запросов и взаимодействие с базой данных.

ХОРОШО:
> За обработку входящих запросов отвечает модуль router.js (8,3 КБ). Он перехватывает HTTP-запросы через middleware-слой Express 4.18 и передаёт их контроллерам — UserController, OrderController, ReportController.

### Правило 5: ПЕРЕХОДЫ МЕЖДУ ПОДРАЗДЕЛАМИ

Никогда не начинай подраздел с пересказа заголовка. Сразу к делу.

ПЛОХО:
> **2.2 Клиентская часть**
> Клиентская часть — важный компонент системы.

ХОРОШО:
> **2.2 Клиентская часть**
> Интерфейс реализован как SPA на React 18.2. Выбор фреймворка обусловлен требованием к динамическому обновлению данных без перезагрузки страницы.

### Правило 6: ПАССИВНЫЙ ЗАЛОГ

Академический текст допускает пассив, но избыток — маркер ИИ. Если в абзаце более двух конструкций «был(а/о) + глагол» — переписать минимум половину в активный залог.

### Правило 7: АКАДЕМИЧНОСТЬ БЕЗ КАНЦЕЛЯРИТА

Текст формальный, но живой. Ориентир — хороший учебник, не бюрократический документ.

ПЛОХО:
> Осуществление процесса тестирования проводилось с целью обеспечения надлежащего функционирования.

ХОРОШО:
> Тестирование проводилось в три этапа: сначала проверялись отдельные модули (unit-тесты), затем их взаимодействие, и наконец — работа системы целиком в Chrome 120 и Firefox 121.

## 4. ЛЕКСИЧЕСКИЕ ПРАВИЛА

### Правило 8: COPULA AVOIDANCE

ИИ избегает «является», заменяя на «служит», «выступает», «представляет собой». Это ловится.

ПЛОХО:
> Модуль служит инструментом для обработки...
> База данных представляет собой набор таблиц...

ХОРОШО:
> Модуль обрабатывает запросы...
> База данных — это набор из 12 таблиц...

### Правило 9: SYNONYM CYCLING

ИИ боится повторять слово и циклит синонимы. Если термин технически точный — повторяй его.

ПЛОХО:
> Модуль UserController обрабатывает запросы. Компонент авторизации проверяет права. Элемент валидации контролирует данные.

ХОРОШО:
> Модуль UserController обрабатывает запросы. Модуль авторизации проверяет права. Валидатор контролирует входные данные.

### Правило 10: FALSE RANGES

Не используй «от X до Y», где X и Y не на одной шкале.

ПЛОХО:
> Работа охватывает вопросы от проектирования базы данных до обеспечения безопасности.

ХОРОШО:
> Работа охватывает проектирование базы данных, выбор технологий, обеспечение безопасности и тестирование.

### Правило 11: ХЕДЖИРОВАНИЕ

Научный текст должен содержать хеджирование, но в балансе с категоричностью. На каждые 2-3 категоричных утверждения — одно хеджированное.

ИИ использует «может», «возможно» в ~4,5 раза чаще человека, при этом почти не использует «безусловно», «определённо». Чередуй хеджирование и уверенные утверждения.

Формулы хеджирования:
- Данные свидетельствуют о том, что...
- По всей видимости...
- Вероятно, это объясняется...
- При определённых допущениях можно утверждать, что...

### Правило 12: ЦИТИРОВАНИЕ

ИИ даёт «Иванов, 2022» без деталей. Называй конкретику: страницу, методологию, числовые данные.

ПЛОХО:
> Как отмечается в ряде исследований, подход показывает высокую эффективность [Иванов, 2022].

ХОРОШО:
> Иванов и Петрова (2022) в эксперименте на 240 испытуемых зафиксировали снижение времени отклика на 34% (p < 0,01) [14, с. 178].

### Правило 13: ПАФОСНЫЕ КОНЦОВКИ — УДАЛЯТЬ

Запрещено:
- «Будущее уже строится сегодня»
- «Это открывает новые горизонты для науки»
- «Данная работа вносит значительный вклад в развитие области»

Последнее предложение абзаца — конкретный вывод или факт, не общая фраза.

## 5. ПРИЗНАКИ ЖИВОГО АВТОРА («ДУША» ТЕКСТА)

Стерильный текст без признаков автора тоже выдаёт ИИ. Добавляй:

**1. Процесс принятия решений:**
> Выбран Express. Изначально рассматривался Fastify из-за производительности, но документация оказалась менее подробной, а middleware для JWT — меньше.

**2. Проблемы и решения:**
> При первой попытке использовался Redis, но выявилась проблема десериализации сложных объектов. Переход на memcached решил проблему.

**3. Ограничения:**
> Система обрабатывает 850 RPS на тестовом стенде. При нагрузке свыше 1200 RPS — деградация из-за блокировок БД.

**4. Эволюция подхода:**
> Изначально планировалось два уровня, но бизнес-логика смешивалась с контроллерами. Выделение сервисного слоя упростило тестирование.

**5. Конкретные наблюдения:**
> Тестирование выявило утечку памяти в модуле экспорта. При генерации PDF > 5 МБ процесс не освобождал буферы.

**6. Information Gain — уникальная ценность:**
Один абзац с реальной конкретикой из проекта обнуляет подозрения на 2-3 соседних абзаца. Конкретные данные, проблемы, неочевидные решения — то, что детектор не может поймать.

## 6. ПРОДВИНУТЫЕ ТЕХНИКИ

### Числовые факты

Конкретные числа резко повышают перплексию. На каждую страницу — минимум:
- Версия библиотеки/фреймворка
- Размер файла в КБ
- Количество записей/запросов
- Процент/время/метрика

### Инверсия порядка слов

В 20-30% предложений ставь обстоятельство перед подлежащим:
> «Для хранения настроек использовался chrome.storage API» вместо «Chrome.storage API использовался для хранения настроек».

### Причастные и деепричастные обороты

Минимум 2-3 на страницу:
> «Проанализировав структуру проекта, удалось выделить пять основных модулей.»
> «Клиентская часть, написанная на JavaScript, взаимодействует с DOM.»

## 7. ЧЕКЛИСТ САМОПРОВЕРКИ

После генерации каждого раздела пройди по этому списку.

### КРИТИЧЕСКИЕ (провал = переписать раздел)

- Ни одной фразы из Категории А?
- «является» не более 1 раза в разделе?
- «данный» не более 1 раза?
- «таким образом» не более 1 раза?
- Нет трёх подряд «список»-конструкций?
- Нет пробелов перед знаками препинания?
- Нет тавтологических повторов?
- Нет copula avoidance (служит/выступает)?
- Нет signposting (рассмотрим подробнее)?
- После заголовка — сразу контент, не пересказ?

### ВАЖНЫЕ (провал = переписать проблемные абзацы)

- Каждый абзац начинается иначе, чем предыдущий?
- Предложения разной длины (5-8 И 25-35 слов)?
- Нет избыточной синонимизации терминов?
- Баланс пассивного залога (не более 30%)?
- Каждая страница содержит числовой факт?
- Каждая страница содержит 2-3 технических термина?

### ДУША (признаки живого автора)

- Есть признаки принятия решений?
- Упомянуты проблемы и их решения?
- Признаются ограничения подхода?
- Видна эволюция решения?
- Есть конкретные наблюдения из процесса разработки?
- Баланс хеджирования и категоричных утверждений?

## КЛЮЧЕВОЙ ПРИНЦИП

LLM использует статистику для предсказания следующего слова. Результат склоняется к наиболее вероятному варианту. Твоя задача — выбирать менее вероятные, но правильные варианты.
